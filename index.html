Every zone, its height budget, and why it sits where it sits.
A · Screen skeleton
Fixed top and bottom, one flexible middle. Only zone 3 is new.
B · Zones
1App bar Back, avatar, name and presence, call, video, settings. Sticky, never scrolls. 54px
2Thread The only zone that grows. Scrolls independently, pinned to the newest message. flex 1
3Recents strip — the redesign Label plus collapse chevron on a 34px row; a horizontally scrolling rail of 64px thumbnails below it. Camera tile first, then the last twelve photos, then All. Three states: open 92px, peek 34px, off 0px. 92px
4Composer ⊕, text field with emoji, mic when empty, send with a count badge when not. 54px
5Safe area env(safe-area-inset-bottom) so the send button clears the home indicator. auto
C · Why the strip sits at 3, not 2

It has to be between the thread and the composer. Above the thread it would compete with the conversation and scroll away. Inside the composer it would push the text field out of the thumb arc. Below the composer it would sit under the keyboard and be invisible when it matters. Zone 3 is the only place where the thumb already rests and where the keyboard pushes it up rather than over it.

H · Design decision

Messenger's attachment menu inverts progressive disclosure: it hides the highest-frequency action — sending a photo taken minutes ago — behind a modal built for its rarest ones, so a photo costs the same six taps as a poll. The redesign surfaces the last twelve gallery items in a persistent strip directly above the keyboard, replacing recall with recognition: the user sees the photo instead of remembering which album it landed in, and the target sits in the thumb's resting arc rather than mid-screen behind a modal. The ⊕ button is deliberately kept rather than removed, so no existing user's mental model breaks — only the ranking is corrected, with rare actions keeping the long path and the common one gaining an accelerator. Because a gallery preview permanently on screen is a real privacy cost on an app like Grindr, the strip ships behind a Show recent photos setting and collapses on demand; that trade-off is a product decision, not a cosmetic one, so it is exposed to the user rather than decided for them.

I · Say this before you're asked

And two taps measures the design, not comprehension: a five-person hallway test would turn this from an argument into evidence.

Design notes
Activity 2 deliverable

Sending a photo you already took

Messenger · the feature that takes too many steps
1 · The problem

The most common non-text message in Messenger is a photo taken minutes ago. It is filed behind an attachment menu whose other seven tiles — polls, games, money, location — are used monthly or never. Sending a photo therefore costs the same as sending a poll: a menu, a permission prompt on first run, an album screen, a load spinner, a grid, and a confirm. The menu is sorted by nothing in particular, so every send begins with a scan of eight identical circles.

2 · Before
Three screens to reach an item that was never more than one scroll away.
3 · After
1Recents strip: the last 12 photos, pre-loaded, above the keyboard. Tap toggles selection in place.
2Send. The composer's existing button now carries a count badge — no new control to learn.
4 · The attachment menu, re-ranked

The menu itself was the second problem: eight equal circles in arbitrary order. It is now tiered. Three large tiles carry what people actually send — All photos, Camera, GIF. The other six move to a labelled list, because rare items are found by reading a name, not decoding a pictogram. Gallery loses its top spot on purpose: the strip already does that job, and two front doors to the same room is worse than one.

6 · Design decision

Messenger's attachment menu inverts progressive disclosure: it hides the highest-frequency action — sending a photo taken minutes ago — behind a modal built for its rarest ones, so a photo costs the same six taps as a poll. The redesign surfaces the last twelve gallery items in a persistent strip directly above the keyboard, which replaces recall with recognition: the user sees the photo instead of remembering which album it landed in, and the target sits in the thumb's resting arc rather than mid-screen behind a modal. The ⊕ button is kept rather than removed so no existing user's mental model breaks — only the ranking is corrected, with rare actions keeping the long path and the common one getting an accelerator. Because a gallery preview permanently on screen is a real privacy cost on an app like Grindr, the strip ships behind a Show recent photos setting and collapses to a single row on demand; that tradeoff is a product decision, not a cosmetic one, so it is exposed to the user rather than decided for them.

7 · Second feature — sending money

Paying someone back inside a chat is the other flow that costs too much. Today you leave Messenger, open GCash, tap Send, choose Express Send, type an eleven-digit number from memory, retype the amount, confirm, wait for the receipt, screenshot it, switch back, and send the screenshot. That is two apps, roughly nine steps, and one number recalled from memory — and the number is where the money actually gets lost, because a single wrong digit pays a stranger irreversibly.

The QR is attached once in settings. After that, paying is amount → send.

Design decision. The failure in the current flow is not the number of taps but the eleven digits recalled from memory: mistyping them sends real money to a stranger with no recall. The redesign removes the recall entirely by carrying identity in a QR the payee attaches once, so sending becomes amount plus one tap and the recipient's own GCash app does the paying. Crucially the app never handles money, MPIN or OTP — it hands off to GCash rather than imitating it, because an interface that asks for those credentials outside the official app is indistinguishable from the phishing pattern GCash and the BSP warn users about. A payment feature that looks trustworthy is worse than one that admits its boundary, so the boundary is drawn in the interface itself: the app moves information, GCash moves money.

8 · What this prototype does not prove

Meta already ships an expandable media tray, so the defensible claim is persistent and pre-loaded, not invented. Two taps measures the design, not comprehension — a five-person hallway test would move this from an argument to evidence. And a browser cannot read your camera roll unasked, so the strip here is seeded with placeholders until you pick real photos: the persistence is simulated, and on native it would depend on the Android Photo Picker.
